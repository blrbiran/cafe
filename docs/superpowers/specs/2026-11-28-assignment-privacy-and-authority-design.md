# Assignment Privacy and Authority

This adds a release boundary to [Host and Caller Authorization](2026-11-27-host-and-caller-authorization-design.md). The first dispatch checkpoint writes recipient copies into the shared journal and still inherits a legacy relay path that synthesizes a shared Order. Separate the durable assignment payload from public state before enabling the new relay contract. This work covers Host Auth Task 4. Caller endpoint selection, replacement, and worker reconciliation retain their own plans.

## Approaches

- Redact assignment events in each UI, detail, and backfill response. This leaves private data in the shared journal and depends on every current and future reader remembering to redact. A restore path can re-expose the data.
- Save a public assignment reference plus an owner-private copy of the exact delivery payload. A separate authenticated relay carries the payload, and all external read paths use the public reference. Use this approach to make the journal safe by construction and keep deterministic retry after restart.

## Contract

- A shared `OrderAssignmentReference` contains `assignmentId`, `targetAgentId`, `targetHostId` and required `bodyHash` (lowercase SHA-256 hex). Thread ID, Order ID, sender Host ID and event ID come from the envelope. Keep the exact target-specific Order in an owner-private payload record keyed by assignment ID. Hash the UTF-8 canonical serialization of `{ order, targetAgentId, targetHostId }` with recursively sorted object keys and preserved array order. Persist owner-only routing variants keyed by Order ID before recording `order.routed`. Both the shared route and future `order.replaced` events carry public data only. Replacement embeds public assignment references and commits the matching private records by ID. Legacy body-bearing records can be read but cannot establish secure delivery authority.
- Shared consumers include peer subscriptions, UI/WebSocket fanout, HTTP Thread detail, SSE history and replay, Root linked detail, `thread/backfill`, search result projections and restart indexing. They consume canonical public envelopes with no assignment body/history and no `decision.variants`. Internal payload tables are accessible only to owner dispatch and recovery.
- Persist the private record before appending the public reference. The public reference commits the assignment. A payload record without a matching reference is inert. A retry resolves the exact reference and immutable copy by ID and checks the digest. A committed reference whose payload is unavailable is a visible dispatch failure. Reclaim orphaned records by bounded reconciliation. Preserve legacy reading without treating a body-bearing assignment as evidence.
- Reserve `assignment-relay-v1` for the Host contract and `assignment-receipt-v1` for Agent queue support. Daemons negotiate the Host capability during `initialize`; the Root exposes only admitted and negotiated Host capability data to its children. The recipient daemon derives the Agent capability from registration and reports it in registry data. Check every hop and the exact Agent before committing a new secure assignment or transferring a private payload. The Root may see the payload in memory while routing it, and persists only the public proof. Omit the payload from logs, journal backfill, and durable Root projections when the Root is not the owner or recipient. Advertise the capabilities when the corresponding authority, receipts and recovery paths are complete. Once enabled, secure delivery fails closed on an unsupported hop.
- The owner keeps the original shared creation and publishes assignment references. The Root and recipient verify the sending Host role and exact creation ID, assignment event ID, Order ID, Thread ID, Agent ID, recipient Host ID and payload digest. The receiver uses the genuine creation event to populate shared history. It has no path for synthesizing a shared creation from a recipient copy. Root retains only the authority evidence required to route and attest. A direct peer cannot claim a third Host's role.
- Use the same type-specific authority check across live event ingress, backfill, direct paths, and replay. Stage missing proof without side effects. Acknowledgement means the event or pending proof is durable. Persist recipient acceptance only after the Agent durably queues the exact assignment. Retry pending work by that ID after checking its status, and replay a durable acceptance without reinjecting work. Recheck expiry after async attachment retrieval.
- A clarification answer requires the original owner capability over protected transport. Only the owner Host can produce the answer's attestation for the exact parent, clarification, recipient assignment, answer request and digest. Use it to derive parent-link verification after reload and during export. A historical claim or a caller-supplied boolean cannot establish verified authority.

## Acceptance

1. An Agent's payload contains only its own variant and authorized history. No other participant's shared or linked view, events, backfill, or recovery projections expose that private copy.
2. Accept an exact retry idempotently. A changed digest, foreign sender, incorrect recipient, or unavailable private copy cannot synthesize state or inject work.
3. Restart between private append, public commit, delivery, and receipt. A missing reference grants no authority, a committed delivery reuses the same ID and content, and a previously accepted assignment is never injected twice.
4. Mixed-version hosts reject unsupported secure delivery before receiving private text. Keep historical events and retained legacy orders readable.
5. Out-of-order event proof, owner attestation, late replies, and early cancellation preserve the Order owner's authority under the main specification.
