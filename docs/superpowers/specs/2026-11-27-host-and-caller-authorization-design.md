# Host and Caller Authorization

## Intent

Protect Cafe task state from a peer that merely knows the shared network token, a caller that guesses a Thread ID, or an HTTP request that supplies another identity in its JSON. A user must be able to cancel only the task they own, operator overrides must be auditable and authorized, and retries from separate callers must never return one another's task IDs or results.

This design is a release gate for real multi-Host use. The current protocol authenticates a shared token but accepts the remote Host name from `initialize`; the current TLS listener does not request client certificates. Event authorization based on local Barista delivery records is useful but does not authenticate a remote Host or forwarded event source.

## Goals

- Give every enrolled Host a stable cryptographic identity independent of its display name or network address.
- Authenticate daemon and peer links in both directions and bind the claimed protocol Host to the authenticated certificate identity.
- Preserve Web UI and ordinary Agent TLS access without requiring a Host certificate.
- Bind relayed events, direct-link events, reports, and backfill to the authenticated sending Host; reject envelopes that claim another Host.
- Authorize cancellation and `replace` against the exact open Order before changing any state.
- Require an operator credential for HTTP `replyAs`; keep operator overrides distinct from Barista-authored replies.
- Scope idempotency by an authenticated caller identity and reject reuse of a scoped key with a different request body.
- Make HTTP provenance truthful: separate authenticated caller identity from caller-supplied display/provenance claims.
- Define a deliberate re-enrollment and mixed-version policy with actionable errors.

## Non-goals

- Per-person user accounts, role management, or a Web UI for managing credentials.
- Replacing TLS, changing the Root relay architecture, or making the shared network token a per-Host secret.
- Automatically aggregating child reports into a parent's direct-reply list. The front door remains responsible for submitting a final report.
- Editing the external dogfooding issue ledger as part of implementation.

## Approaches considered

1. **Keep the shared token and validate more claimed fields.** This is small, but a token holder can still claim another Host, Agent, or operator. It does not establish event origin and is rejected.
2. **Sign every event with a per-Host HMAC secret.** This can authenticate journal events, but creates a second protocol for enrollment, rotation, and relay, and does not authenticate the transport peer or naturally protect non-event RPCs.
3. **Use Root-issued Host certificates for mutual TLS, with explicit one-time enrollment.** The Root assigns and persists a stable `hostId` against each Host public key. Daemon/peer sockets must present that certificate, and the authenticated `hostId` is checked against the protocol handshake and every relayed event. The existing shared token remains a bootstrap/API credential. This is the recommended approach because TLS already exists, certificates are already Root-issued, and the trust check runs before RPC dispatch.

## Design decisions

### Host enrollment and identity

- A Host identity is an immutable random `hostId`, distinct from `host` (the local routing/display slug), `displayName`, aliases, and address.
- An enrolled Root has a stable `rootHostId` in its Root CA metadata and leaf certificate. `cafe connect` first discovers the public CA and rootHostId without sending credentials, then verifies the Root leaf over TLS against the supplied CA fingerprint or first-use TOFU pin and checks its signed hostId before sending the token or invitation. It pins that hostId together with the CA fingerprint. Later Root address changes do not change rootHostId. The TLS handshake response must match the pinned rootHostId before outbound RPC handlers become usable. Root CA rotation in place is unsupported; replacing the Root CA requires explicit network re-enrollment. Root leaf-key renewal under the same CA and rootHostId is supported.

- `cafe host invite [--name <display-name>] [--replace <host>]` runs locally on the Root. It reads the Root's local operator credential; the network token alone cannot mint invitations. It creates a short-lived, one-use enrollment invitation stored hashed, expires after 30 minutes, and is consumed atomically. The invite records the expected previous hostId/key/revision for a replacement.
- The joining Host generates and durably saves its private key, requestId, and request nonce before redeeming the invitation. Redemption binds the invite to that public key and the requested SAN set. If the response is lost, retrying the same invitation/requestId/public-key fingerprint/SAN hash returns the same hostId and certificate before rechecking the old-binding precondition; this exact retry remains valid after the invitation's 30-minute redemption window. A different key, requestId, or SAN hash is refused. The Root retains the consumed result while that key binding is current. After re-key, it retains a non-secret tombstone (invite digest, requestId, SPKI, hostId, superseding revision) and returns `credential_superseded` without the old certificate. Re-key replacement compares the expected old hostId/key/revision and offline state atomically at first commit; a stale invitation fails without consumption.
- `cafe connect <root> --invite <code> [--ca-fingerprint <sha256:...>]` keeps the existing Root CA bootstrap and leaf-issuance flow, but redeems the invitation at `/api/tls/leaf`. It sends only the public key, stable requestId/nonce, and canonical SAN list computed from the local Host addresses. The Root assigns and persists hostId and signs a certificate binding hostId to that key. The private key never leaves the joining Host. A provided CA fingerprint must match; omitting it retains the existing documented TOFU behavior.

- Reconnect and certificate renewal preserve the same hostId and key binding. A changed key cannot claim an existing hostId. Re-keying requires a new invitation and `--replace <host>`; it preserves the hostId and atomically replaces the stored key fingerprint, revoking the old fingerprint at the Root. Connected peers receive the new binding and drop existing sockets for the old fingerprint. A peer disconnected from Root may continue to accept the cached old certificate only until its existing certificate expires; Cafe must report this bounded offline revocation window and must not claim immediate network-wide revocation while Root is unreachable. For an expired leaf, the Host requests a short random renewal challenge from the Root over the Root's pinned TLS listener, signs it with its persisted private key, and sends the proof plus required API token. The Root verifies against the enrolled public key before issuing a replacement leaf. Renewal does not require a currently valid client certificate or a new invitation. If Root is unreachable or the Host certificate is expired at startup, the daemon runs local-only TLS and keeps retrying enrollment/renewal; it never falls back to plaintext or connects to peers with an unverified identity.

- A Host certificate includes both serverAuth and clientAuth usages. Its signed identity SAN carries hostId; DNS/IP SANs remain dial-name checks and never establish identity.
- The Root persists the mapping `hostId -> routing host slug, key fingerprint, enrollment state`. The canonical routing slug for an enrolled Host cannot be changed by `initialize.host`; display renames remain separate. New Hosts receive collision-free routing slugs; an invitation that replaces a record is the only path that retains that record's slug.
- The shared Root token remains required by the existing API/bootstrap contract where applicable, but it cannot enroll or replace a Host without an invitation. Renewal requires proof of possession of the enrolled private key, not the shared token alone.
- The existing TLS listener remains shared. It requests a client certificate with `rejectUnauthorized: false` so Web UI and Agent connections can still connect without one. After `initialize.kind` identifies `daemon` or `peer`, Cafe requires a TLS-authorized client certificate, verifies the Root CA and hostId mapping, and checks the handshake fields before binding any RPC handlers. A missing/invalid certificate is rejected before registry, Order, or event methods are bound.
- Outbound links present the local Host certificate. A Root uplink is accepted only when the server certificate hostId equals the pinned rootHostId; a direct peer is accepted only when its certificate hostId equals the intended known Host ID. For enrolled Hosts, the Root-authenticated `hostId -> current SPKI` binding is authoritative and replaces legacy address-only TOFU pins; all peers refresh the complete binding map before enabling RPC after reconnect. Re-key updates that binding and closes every connected socket authenticated under the old SPKI. A peer isolated from Root may use its cached hostId/SPKI binding only until the cached certificate expires; after expiry it refuses the link until Root refreshes the binding. The client installs Root/peer RPC handlers only after certificate, hostId, SPKI, protocol version, and capability checks pass. A Root address change keeps the same rootHostId; it never resets the identity pin.
- Introduce a `host-auth-v1` capability. A child/peer without it receives a stable `host_auth_required` error and upgrade/re-enrollment guidance. Do not silently downgrade daemon or peer links to shared-token identity.
- Existing unauthenticated remote Hosts require explicit re-enrollment. A local Root can continue operating alone. The error and `cafe doctor` must identify the old Host records that need enrollment; no automatic first-claim migration is allowed.

### Event origin and relay

- Every event envelope carries immutable `eventHostId` (the Host that created that event), separate from the Order's `from.host` and the legacy `host` display/routing field. The authenticated actor is `{kind, principalId}` where kind is `human`, `connector`, `agent`, or `operator`. principalId is an opaque stable ID; Agent uses agentId, while human/connector/operator IDs are generated and mapped to local credential digests at the credential-owning Host. Never copy raw keys or reusable key digests into event bodies. `origin` and `via` remain separate provenance claims.
- A registered Agent may request a human clarification only by `escalate` from an exact delivered human Order and only when that Order's owning Host advertises the capability. This creates the clarification child Order under the Agent's identity and preserves the exact parent Order link; it does not authorize a human answer. Human-only clarification/report eligibility checks `actor.kind`, not string prefixes or asserted origin.

- The Order-owning Host persists the authoritative `order.created` and a per-target `order.assigned` event before sending `order/relay`. Assignment includes a unique assignmentId, exact Order/Thread, target Agent and target Host, and the target-specific body/history. The relayed payload carries the canonical Order event ID and assignment event ID; the target verifies their hashes and can never synthesize a trusted `order.created` from a mutable target copy. A replacement assignment may instead be embedded in `order.replaced`, which is canonical creation and assignment evidence for the replacement turn. Unicast fallback emits and persists a new assignment after the preceding target's terminal or delivery-failure state.

- A recipient Host persists an assignment in its inbox before forwarding it to the registered Agent. The Agent acknowledges the exact assignmentId only after its local session queue has durably recorded it; the Agent's persistent queue deduplicates the same assignmentId across reconnect/restart. The recipient then records `order.delivered`; this evidence is required for later Agent ack/heartbeat/reply/decline/report. Repeating an accepted assignmentId returns the existing receipt and cannot start another turn. If delivery or Agent acknowledgement fails, the recipient reports `order.dispatch-failed` to the owner Host; only the owner records the failed target and decides whether to fall back. On recipient restart, an Agent with a durable queued assignment replays only its acceptance receipt, never the task injection; the recipient persists the recovered receipt so a later final reply remains auditable. A recipient with no durable Agent receipt asks the owner for assignment status and retries the same ID only if still active; if status is unavailable it waits, and if superseded/closed it never injects. Transport is at-least-once, logical acceptance is idempotent.
- The owner may start a fallback once it has an authenticated delivery-failure report or the assignment/Agent lease expires without acknowledgment. An old assignment remains authorized for a late final reply while the Order is open. A late ack/receipt never cancels a fallback or restores its target state; a late final can win the target's serialized terminal transition once, and later attempts become audit-only. Thus fallback work may overlap with a delayed original attempt, but only one result changes the Order.
- Root ingress validates exact `(orderId, threadId, assignmentId, agentId, eventHostId)` against the authoritative Order, assignment, and recipient delivery record. Event authority is type-specific: `order.created`, `order.assigned`, `order.replaced`, `order.cancelled`, `order.closed`, `order.failed`, and coordinator-generated `skipped` states are authored only by the Order-owning Host; `order.delivered` and dispatch-failure reports are authored by the assigned target Host; Agent ack/heartbeat/reply/decline/report are authored by the registered target Agent on that Host. Human/connector actions are authored by the Order-owning Host and identify an opaque actor principal whose secret is retained only at that Host.
- When the person answers, the Order-owning Host verifies the original human owner capability over loopback or Root-CA-verified TLS and verifies that the clarification was created by an exact delivered target. It creates the human-authored follow-up `order.created` in the existing clarification Thread with a one-use `parentOwnerAttestation` bound to parent Order/Thread, clarification Order, recipient Agent/Host, answer request ID, and hash of the answer body. The attestation is carried inside that authenticated owner-Host event, contains the opaque actor principal but no owner secret, and is durable with the answer. `parentOwnerVerified` remains derived local metadata after this event validates; never accept it from an HTTP caller or as cross-Host proof. Equal answer retries return the same Order; a different answer to the same clarification conflicts. The parent Thread's original `from` remains unchanged.
- Root or a direct receiver that gets an event before its canonical creation/assignment (`order.created` or `order.replaced`) durably stages it without applying state or notifying clients. It requests the canonical Order/assignment from the owner Host and replays only after validation. Pending staging is persistent across restarts and bounded; if it fills or cannot be persisted, the sender gets an error and retains/retries its journal. A successful backfill acknowledgement means each envelope is durable in the normal journal or pending journal. A later owner assignment/creation arrival drains the pending queue exactly once.
- Every receiver validates authority before applying state. Only the Order-owning Host may close/cancel/fail the shared Order; a recipient can report delivery failure but cannot close it. Agent state events require registered identity, matching eventHostId, assignment, and delivery evidence. Enforce the same checks on direct links, Root ingress, and backfill.
- On `thread/event` and `thread/backfill`, a direct peer may submit only events whose `eventHostId` equals its authenticated Host ID. Root validates the source and Order authority, persists it, then relays it as the trusted attestor without rewriting eventHostId or actor. A child receiving a Root-relayed event trusts the authenticated Root connection. No per-event signature is required for Root-mediated relays.
- A child backfills only envelopes authored by its own eventHostId. Events learned from another Host while Root is offline are not backfilled by the receiver; the source Host backfills them after reconnect. During Root outage, direct links accept only events created by the authenticated sender; Cafe does not relay a third Host's events through a child.
- Replaying an event is idempotent. Once an Order closes, replay may add an authorized late final reply to audit history but cannot reopen the Order, change targets/terminal state, or clear a newer active order. Legacy events remain readable and are labeled legacy/unverified; do not retroactively claim they were authenticated.

### Caller credentials and task ownership

- The human owner credential is a client-generated random capability. The Daemon accepts a well-formed credential on first use, stores only its digest with the created Order, and never requires a separate registration. CLI/Web use their existing stable local/browser credentials; stdio MCP uses a separate stable credential under the same `CAFE_HOME`. The value is never copied into another Host's event history. A registered Agent uses its protocol peer identity instead. Caller ownership is per Order; a later turn on the same Thread may have a different human, connector, or Agent owner.

- Add `orderId` to cancel requests. A human caller must prove the matching Order owner credential. A registered Agent may cancel only an Order it created; a Barista that received an Order cannot cancel the whole shared task on behalf of the requester. An installed HTTP connector may cancel/replace only Orders created under its own connector credential. Cancellation of a team task by another recipient remains a requester/operator action.
- Replace the boolean `replace` with `replaceOrderId`. Before making a follow-up replacement, the client resolves the current open Order once and sends that exact ID. The server checks it is still the same open Order and that the caller owns it. It validates request fields and computes an accepted route with at least one target before any state change; route failure/no targets leaves the old Order open. After any asynchronous routing, it rechecks the old Order ID and open state under the per-Thread transition lock immediately before commit; a final reply, cancel, or competing replacement that won the race returns `stale_order`.
- Commit an accepted replacement as one durable `order.replaced` journal event on the Order-owning Host. Before append, persist the new Order's owner digest/actor binding in local SQLite; an orphan binding without a journal event is ignored and cleaned up. The event names the exact old orderId, full new Order, validated route decision, and stable assignmentIds. The Store indexes the replacement event under both old and new Order IDs, and recovery projects old closure plus new open state even if metadata writes did not finish. Receivers durably stage it until the old Order is known. After append, dispatch failures belong to the committed new Order and are recovered/retried by assignmentId; they never reopen the old Order.- The idempotency cache remains bounded and process-local. Within its live window, an identical scoped retry returns the original replacement result before checking the current order. After daemon restart or cache expiry, a retry with the old replaceOrderId returns `stale_order`; it never affects the newer Order. This bounded replay contract does not promise returning the original response across restart.
- `cafe cancel <threadId>` may resolve the current open Order once for compatibility, but must send its orderId and verify the owner credential against that exact Order. Web Stop sends both threadId and orderId and its existing per-browser owner credential. For another caller's or an unverifiable legacy Order, `cafe cancel --operator <threadId> --order <orderId>` explicitly uses the local operator credential and records the operator as the actor.
- Legacy Orders without an owner digest are not cancelable through the human-owner route. Operator cancellation always requires an explicit orderId when no valid owner credential is supplied.
- HTTP connectors use a separate caller capability per installed connector. `cafe connector install` generates a random key, stores only its digest in local Daemon state, and injects the secret into that connector's environment through its protected local config. The credential is bound to the same `CAFE_HOME`/host where the connector is supervised; `install --force` preserves the same connector principal, and remove revokes it after the process is stopped. A connector configured to post to a different/remote Daemon must instead be installed on that target Host; Cafe refuses to send the secret to a daemon that has not provisioned it. The connector identity/key is not the shared network token or a self-asserted connector name.

### Operator overrides

- Preserve `replyAs` as an operator override for CLI/MCP use; do not treat target matching or a loopback socket as caller authentication.
- Add a separate local operator credential, generated once by the daemon with exclusive-create semantics and stored mode 0600 under `CAFE_HOME`; store only its digest in daemon state. CLI/MCP can read the local credential and send it in a dedicated header. Never print or log the secret. Sensitive `replyAs`, explicit operator cancellation, and Root invite creation require it even on loopback. The shared Root token and an Order owner key alone are insufficient for an override.
- Operator authority is local to Orders owned by the Daemon in the matching `CAFE_HOME`; the operator credential is accepted only from loopback. `cafe reply --as`, `cafe cancel --operator`, and `cafe host invite` fail with an actionable message when pointed at a remote `CAFE_DAEMON` or a Thread whose originating Host is not local. Run the operation on the Order-owning Host. No operator secret is forwarded across Hosts.
- The stdio `cafe mcp` server does not expose `cafe_reply` by default. `cafe mcp --operator` is an explicit opt-in that enables `cafe_reply` and loads the local operator credential; the tool may only override a locally owned Order. Ordinary MCP `cafe_ask`/`cafe_cancel` use the MCP owner credential and may act only on that MCP caller's Orders.
- The override must name an explicit orderId and an assigned target whose state is `pending`, `acked`, `failed`, or `skipped`; it cannot add a target, replace a final Agent reply, or replace a previous override. Persist a separate `order.overridden` event with operator actor, targetAgentId, and text; never fabricate an Agent ID as the author. `cafe reply --interim` is allowed only while the Order and target remain nonterminal; it adds a note and does not change target state.
- The Order-owning Host serializes final Agent replies and operator overrides under the same target transition lock. The first accepted terminal event wins. If the Agent final reply wins first, override returns `target_already_final`. If the operator override wins first, that target becomes `overridden`/terminal and all outstanding assignments for that target are superseded/cancelled; later Agent replies are audit-only and cannot alter the result or statistics. For `collect: any`, a final override may close the Order and suppress remaining deliveries; for `collect: all`, it terminalizes only that target while the others continue. Overrides never count in Agent answer/decline statistics and are visibly labeled in Web, CLI, MCP, and event history.

- Ordinary Barista replies continue through registered RPC identities and delivery evidence. No HTTP request can create an authenticated Barista event.

### HTTP provenance

- Every HTTP-created Order requires either a verified human owner credential or an installed connector credential; without one, return `caller_identity_required`. Derive `from` and callerScope from that credential, never from `as`. CLI/Web use their owner key; stdio MCP uses its stable local owner key; an HTTP connector uses its connector-specific key. The operator credential authorizes administrative overrides but does not silently turn an Order into a customer request.
- Owner, connector, and idempotency capabilities may be sent only over loopback HTTP or a Root-CA-verified TLS connection. Remote plaintext HTTP requests to create/cancel/replace Orders are rejected with `tls_required`; callers can continue using the local loopback API without TLS. An unverified or shared API token never substitutes for TLS protection of these credentials.
- Never treat `as`, `origin`, or `via` as authentication. Keep caller-provided `as`/`via` and `origin: agent` only as explicitly unverified claims, carry a `provenanceVerified: false` marker, and label the claims as unverified in Web/CLI/MCP views. This preserves the CLI/MCP explicit `--origin agent --via` workflows without presenting them as authenticated. Registered Cafe Agent RPC continues deriving identity from the peer and may record verified `origin: agent`/`via`.
- HTTP cannot claim a registered Agent identity merely by setting `origin: agent` or `via.address`; such fields never grant Agent authority, parent-link authority, or access to an Agent's idempotency scope. A registered Agent must use the protocol API for those operations.
- New event/report audit records retain authenticated actor identity and asserted display provenance as separate fields.

### Idempotency

- The idempotency cache key is `(callerScope, idempotencyKey)`, where callerScope is derived from a registered Agent ID plus authenticated Host identity, a verified connector identity, or a digest of the human owner credential. It is never derived from `as`, `via`, address text, or an untrusted Host claim.
- Requests with `idempotencyKey` and no authenticated caller scope fail with `caller_identity_required`; they are not placed into a global namespace.
- Store a stable hash of the canonical request with each cache entry. Reuse of the same scoped key and same canonical request replays the original result. Reuse with a different request returns `idempotency_conflict` and does not create or expose an Order.
- Preserve the current bounded in-memory cache window and retry behavior after failed creation. Document that idempotency is process-local and time-bounded.

## Migration and compatibility

- Keep `PROTOCOL_VERSION` compatibility checks, and separately advertise `host-auth-v1` and `caller-auth-v1`. Any remote daemon/peer RPC that could mutate registry, Orders, reports, or events requires host authentication; new clients must preflight `caller-auth-v1` before exact-order cancel/replace and refuse before sending credentials to an older daemon that ignores orderId. HTTP handlers enforce credentials server-side even when a client omits the preflight.

- Add an explicit re-enrollment path for existing Hosts. Do not infer identity from old `host` strings, `url`, or `knownDaemons`.
- Local single-Host operation and UI/Agent connections remain available. A Root with old child records must show a clear action per child rather than silently marking it trusted.
- Existing event files and databases are preserved. Legacy Orders may lack owner credentials and legacy events may lack authenticated origin; display that boundary and require the operator path for actions that cannot be proven.
- Do not publish or claim physical multi-Host readiness until a real second Host and mixed-version matrix pass.

## Acceptance criteria

1. Two enrolled Hosts have distinct stable hostIds. A Host cannot connect using another Host's id/slug, even when it knows the shared network token. Re-keying preserves the hostId, revokes the old fingerprint at Root, and updates connected peers; documentation and doctor state the bounded stale-certificate window for peers isolated from Root.
2. A daemon/peer WSS connection without a valid client certificate is refused before any RPC handler is registered; UI and ordinary Agent access still work without a Host certificate.
3. Root uplinks pin rootHostId independently of address. A wrong Root certificate/hostId or wrong direct-peer certificate is rejected before installing handlers. An expired child leaf can renew over the pinned Root TLS endpoint through signed proof of the stored private key; without Root reachability the child stays local-only and retries.
4. A certificate with a mismatched hostId, changed/revoked key, wrong Root CA, or unapproved peer identity cannot register, relay, backfill, or alter a Host's Registry record.
5. An event sent by a direct peer must be authored by that peer Host and be authorized for the exact Order. Root validates event type, target/delivery evidence, actor, and order owner before applying or relaying it. Out-of-order recipient events are held without side effects until the authoritative Order and delivery evidence arrive; they then apply exactly once.
6. A child can backfill its own authored delivery/reply/report events but cannot backfill an event authored by another Host. Root is the only attestor of cross-Host relays; offline direct links accept only the authenticated sender's own events.
7. A non-owner cannot cancel another caller's Order through protocol or HTTP. A well-formed human owner credential is accepted on first use and stored as a per-Order digest; connector credentials work only after local provisioning. A registered Agent can cancel only its own Order. A stale orderId cannot cancel a later Order on the same Thread.
8. An unauthorized, invalid, or unroutable `replaceOrderId` leaves the existing Order open. An authorized replace uses one durable `order.replaced` transition for the exact old Order and creates one replacement; recovery cannot leave half a replacement. An identical scoped idempotency retry within the cache window replays the original result without touching any newer Order; after restart/expiry, a new request with stale orderId returns `stale_order`.
9. HTTP `replyAs` without the local operator credential fails on loopback and remote listeners; operator credentials are accepted only on the matching local Daemon and only for locally owned Orders. MCP does not expose `cafe_reply` unless launched with `cafe mcp --operator`. An override may target an assigned `pending`, `acked`, `failed`, or `skipped` target; it never creates an Agent-authored event. It can finish a `collect:any` Order or mark one target overridden in `collect:all` while other targets remain pending. A later Agent reply cannot reverse a final override.
10. An HTTP caller cannot create verified Agent origin/via by setting JSON fields. Asserted display provenance is visibly labeled unverified. Owner/connector/idempotency capabilities are refused over remote plaintext HTTP.
11. Two callers using the same raw idempotency key receive separate Orders. Within one caller scope, identical requests replay; a different payload returns `idempotency_conflict`. CLI, Web, stdio MCP, registered Agent, and installed connector scopes are distinct.
12. Human owner keys and operator/connector credentials are stored only as digests on the local daemon where needed, never copied into event bodies, logs, or another Host. Connector install/force/restart keeps the same provisioned principal; removal revokes it after stop.
13. `cafe doctor` and CLI connection errors explain how to enroll/re-enroll a Host and identify unsupported mixed-version peers. Local operation remains available while enrollment/renewal is pending.
14. Existing Web UI, Agent RPC, CLI/MCP creation, CLI/Web cancellation, connector retries, and approved reporting flows remain covered by regression tests.
15. No production Root restart, external ledger edit, npm publication, or physical second-Host claim is part of local implementation verification.

## Calls left to implementation

- Choose the certificate identity extension/SAN encoding and keep it verifiable with Node's TLS APIs.
- Choose a collision-safe hostId representation and database migration that leaves all existing routing/display names intact.
- Design invitation storage with one-use atomic consumption and a safe CLI output path.
- Keep error messages plain-language and translate them in CLI/Web where those surfaces currently localize API errors.
