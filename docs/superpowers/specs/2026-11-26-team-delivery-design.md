# Cafe team：派单、回问与汇报

本文供维护者决定交付范围，也供实现者查阅验收条件。用户已选定保留单一前门、让委派可见、减少无关唤醒的方向。先读下文示例，再按交付批次验收。

**实现约束**：团队只有一个接单前门。派单、广播和回问各有明确收件范围。每个 Thread 同时最多一个活跃 Order。用父子 Thread 记录委派。任务拆分和合入由协作者决定，Cafe 负责通信和记录。

## 用户看到的行为

例如，用户向 `parser` 团队说「为新增语法补单元测试」。只有前门收到原单。前门根据名册选择 `tester`，在关联子 Thread 中显式派单。用户从原会话看到「测试：进行中」。测试成员有问题时回问实际派单人。若前门需要人决定测试范围，原会话显示待答澄清。测试完成后，原会话能看到对应的结论和子会话入口。前门可以直接回答简单咨询，详情可根据实际子 Thread 显示「前门回复」或「已委派给测试成员」。这里的委派证据是实际子单，前门的文字声明仅是进度说明。

## 方案取舍

| 方案 | 结果 |
|---|---|
| 保留当前前门和显式寻址 | 交付最快，测试者仍可能遇到错队、回问断开和完成状态失真。 |
| 单前门配合安全寻址、可见委派和安静通知（选定） | 扩充现有 Order 与 Thread 的用户体验。用确定性的寻址限定收件人，用现有会话展示任务进展。 |
| 内建任务引擎 | 可以强制执行依赖、重试与验收策略，维护成本和权限范围更大。 |

## 执行边界与名册

`.cafe` 中记录支持的宿主名称。托管进程接受 `pi`、`omp`、`codex` 或 `claude`，已有的 `bin: pi` 和 `bin: omp` 可兼容，实际可执行文件由本机 Cafe 启动配置解析。校验团队配置后才发布或启动，恢复持久化 worker 时同样校验。无效配置应给出字段和允许值，整队不部分启动。外部目录是否允许写入属于单独的本地授权问题，尤其是仓库配置里的兄弟 worktree 路径。

`team start` 或 `team sync` 首次发布时，记下本机名册目录的真实路径。后续同 Host、同团队名、同 channel 的发布必须来自这个目录。经符号链接访问同一实际目录仍算同一来源。成员注册只更新在线状态，可以使用 worktree 副本识别自身。旧记录尚无发布目录时，由下一次显式发布认领。只有显式发布可以修改权威名册、接管旧记录或恢复已移除的团队。跨 Host 续用现有同步和修订规则。

## 寻址与接单

| 请求 | 收件口径 |
|---|---|
| 向团队发起新单 | 唯一权威名册的唯一在线前门。多个候选或前门不合格时显示原因。前门向自己发新单时提示显式派单。 |
| 点名成员 | 解析具体成员。保留显式跨队点名能力。未给 channel 的新单从已解析的团队收件人取得 channel，保存、路由和追问共用这一值。 |
| 点名 duty | 根据发送方所属权威团队或明确且唯一的团队范围查名册。成员不存在、成员离线和有多个匹配者给出不同结果。共用 channel 时严禁猜测另一队。 |
| 明确要求广播 | 有团队范围时只发给本队在线可接单成员。共享 channel 无法唯一确定团队时拒绝。`collect: all` 等到每个目标终态或截止。 |
| 继续对话 | 普通前门对话继续交给前门，具体成员的子 Thread 继续交给该任务的相关收件人。多人回合后的隐式追问需要确定一个收件人或提示选择。显式目标可覆盖。 |

职责名称和短语别名由团队配置。所有发给团队的新自然语言请求仍先到前门。别名是前门选择显式 duty 的参考，可在测试中用确定性的前门验证选对 `developer` 和 `tester`。任意自然语言的语义识别由前门负责。找不到唯一合适人选时，前门澄清或自行回答。强制委派留给显式选项，先交付可见派单结果，再决定是否需要加该选项。

## 回问、进度与上下文

Agent 回问仍使用实际父 Order 与派单者关系。对人的澄清挂到原始的人类 Thread，作为需要回答的事项。人应能从原会话回答，答案继续交给提出澄清的成员。路由不到对端时报告明确状态。任何回问均不进入通用路由。用简短的父任务摘要和参照标识帮助子任务收件人理解上下文。避免把不相关成员的全文历史注入追问。

前门「已派单」属于进度。聚合状态需要分别表达前门回合是否结束、已链接的任务是否仍在执行、是否有待人澄清。子任务终态对父会话可见，即使前门已回复。前门负责面向请求者写最后总结。实现者可选择最小的事件和展示方案，审核时应重点检查重连、迟答、截止和多轮相关性。子任务结论只关联到对应父单。

Observer 摘要是被动信息。默认展示或按需读取有限条目，且不单独启动模型回合。保留 Root 在线时的统一摘要发布和离线接管。一个 `collect: all` 回合结束时，发单方收到一次足以继续工作的结果通知。每条分段回复继续记录；已结束回合的迟到回复只供查看。

## 交付顺序与验收

1. **启动与名册**（#178、#177、#189）。不支持的宿主值在发布或创建 worker 前失败。过期 worktree 注册或尝试发布后，原名册成员和 revision 保持稳定。从权威目录同步可以正常增删成员。
2. **正确收件**（#142、#151、#163、#164、#169、#174、#192）。使用两个共用 channel 的团队验证 duty 与广播从不误投。团队收到目标仅为有效前门的首单，且无 channel 的点名首单能在同 Thread 继续追问。前门自投递被拒。pi/omp 显式广播转发到 daemon。
3. **完成回路**（#120、#121、#145、#171、#187、#193、#194）。人发单、前门派单、成员回问、人回答、成员完成。CLI 和 Web 可知当前需求以及最终结果，前门的过程回复不造成虚假的任务完成。用同机确定性 agent 验收，再在第二物理 Host 可用后检查同一路径。
4. **收敛上下文与可见性**（#71、#168、#172、#175、#176）。记录新单、追问、结果与摘要分别启动的模型回合。默认 digest 唤醒数为零。用同目录启动的前门、开发和测试成员，验证写代码和写测试分别进入所需成员的子 Thread。确认简单咨询不产生额外 Order。补上首次启动指引（#173）。

#72 现有 `collect: all`、显式广播与 agent 回问的验收继续保留。#179 属于独立的日志恢复工作，不能用团队端到端通过推定其修复。涉及 Web 界面的取舍，先做草图供用户审阅。

## 独立审查后的实施口径

- 一个广播回合是一个 Order，有多个独立 target 状态。每个委派子 Thread 有自己的 Order。继续沿用 `collect: all` 的截止时间和 skipped 状态。
- 名册目录固定在所属 Host 的本地持久化记录中，无须在网络或 Web 暴露。首次发布取本机真实目录，旧记录在首次显式发布时认领。移除保留目录归属。目录迁移需单独设计。旧 daemon 继续执行旧语义，先升级名册所在 Host。无效的持久化配置由恢复流程逐项拒绝并记录原因。
- 第一轮自然语言请求始终到前门。职责别名供前门派第二条 Order 时使用。无归属且无法唯一确定团队时，返回可读的错误并提示指定范围。
- 人类澄清由发出澄清的 agent 拥有。人类答复只寻址该 agent，离线时保留待答状态并显示原因。CLI/Web 同时显示当前 Order 状态和关联子任务状态。前门最终答复仍关闭自己的 Order。关联子任务完成不替前门生成总结，也不改写已关闭 Order 的状态。
