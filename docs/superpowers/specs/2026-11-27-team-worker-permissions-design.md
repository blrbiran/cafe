# Team Worker Permissions and Directories

## Intent

A team's `.cafe` file describes work that may be written by managed Baristas. The current daemon accepts directory traversal and can launch multiple write-enabled workers in one working directory. It also accepts `access: read-only` while Pi/OMP keep their default write tools. Make the boundary truthful and enforce it before any worker starts.

## Goals

- Enforce `access: read-only` for every Cafe-managed headless worker, including pi/omp.
- Make managed headless workers read-only when `access` is omitted; writes require an explicit roster setting.
- Refuse a read-only declaration on a TUI member because Cafe cannot restrict tools in a user-owned terminal session.
- Prevent `.cafe` from silently granting access to arbitrary host directories. Keep common in-repository worktrees usable and allow an operator to authorize an external path locally.
- Reject overlapping write scopes for two Cafe-managed members on one Host.
- Require a TUI Barista to register from the exact canonical directory configured for that team member.
- Reconcile supervised workers when the authoritative roster removes a member or changes its directory, runtime, or access level.

## Non-goals

- OS-level sandboxing that guarantees protection against a compromised agent runtime or an agent that exploits a runtime bug.
- Changing permissions of an existing TUI session or hiding files from read-only workers; read-only means no write-capable tool is exposed.
- Preventing two different users or processes outside Cafe's supervisor from editing the same repository.
- Automatically moving project worktrees or changing Git layout.

## Approaches considered

1. **Reject every directory outside the roster root.** This blocks traversal, but breaks sibling worktrees that a person deliberately created for team members.
2. **Allow any absolute or parent-relative path from `.cafe`.** This preserves current flexibility but makes repository configuration a local filesystem authorization grant; a malicious or mistaken roster can write arbitrary paths.
3. **Default to the roster root and require a local per-member grant for canonical external directories.** This keeps repository config portable while the Host operator controls which external worktree each member can access. This is the recommended approach.

## Design decisions

### Access levels

- For all Cafe-supervised headless Baristas, including standalone `cafe barista start`, omitted `access` means `read-only`; `--write` or roster `access: write` is the explicit opt-in to workspace writes. Preserve existing access schema spelling.
- Headless Codex/Claude continue using their existing read-only/workspace-write launch flags. A user-owned TUI (both roster `mode: tui` and `cafe barista start --agent codex --tui`) uses the host application's permissions; Cafe must not label it as enforced read-only/write. A legacy roster TUI `access` field is ignored with an actionable warning. The `--write` flag must never imply Cafe controls a TUI session's sandbox.
- Pi read-only workers use only built-in `read`, `grep`, `find`, `ls` and Cafe's `cafe_ask`, `cafe_agents`, `cafe_reply`, `cafe_decline`. OMP read-only workers use its supported built-ins `read`, `grep`, `glob` and the same Cafe tools; OMP's semantic `find` tool is excluded. Cafe passes a strict per-runtime `--tools` allowlist. Pi disables MCP with `--no-mcp`; OMP has no equivalent flag in the supported CLI, so no namespaced MCP tool is included in its explicit allowlist and none is callable.
- For both Pi and OMP, read-only launch disables automatic user/project extension discovery and explicitly loads only the Cafe extension (`--no-extensions` plus Cafe's explicit `-e` path). This prevents another extension from overriding an allowlisted built-in name. If a runtime cannot disable automatic extensions, parse the exact tool allowlist, or load the explicit Cafe extension while in RPC mode, Cafe refuses the read-only launch before worker spawn.
- Read-only Pi/OMP launch is enabled only for versions in Cafe's tested compatibility table. Initial entries are Pi 1.6.0 and OMP 19.0.1, with the exact allowlists above. A new runtime version stays unsupported for read-only until a no-model integration test proves its allowlist and extension-isolation behavior; `--help` flag presence alone is not proof.
- Runtime preflight keys a no-model isolation probe by executable realpath/SHA-256 plus Cafe-extension version/hash. On a cache miss, it launches the runtime with an isolated temporary profile and fake MCP server, uses an inert Cafe-tool stub, and attempts a direct RPC call to an unlisted namespaced write tool; the tool must be unavailable and the fake server must not perform a side effect. Pi additionally uses `--no-mcp`. The probe never loads user project extensions/config, never connects to the real Cafe daemon, and never requests a model. Cache success only for that exact executable+extension hash; a same-version binary replacement triggers a new probe. If OMP exposes MCP tools or aliases despite the allowlist, OMP read-only is refused for that binary.
- Legacy `access` declarations in `.cafe` are ignored for TUI members. Cafe reports that the terminal manages their permissions.
- The supervised Codex `--tui` adapter is treated as host-managed, not as a Cafe-enforced sandbox; its access label cannot claim `read-only` or `write`.
- Web, CLI, daemon records, and worker status display the effective managed access level. For roster TUI sessions, display `managed by host`.

### Directory authorization

- A member `dir` is a relative path resolved from the canonical roster root. Reject empty paths, absolute paths, NULs, and malformed path segments before any launch or roster publication. Parent-relative `..` is accepted only when the exact resolved external target has a local grant.
- Resolve both roster root and member path through `realpath`. By default, the member path must remain within the roster root after symlink resolution; lexical containment alone is insufficient. The same rule applies to read-only and write-enabled members because an external directory exposes local data even without write access.
- An external path can be used only after a local operator explicitly grants it for the exact canonical roster root and member. Add `cafe team trust-path <rosterDir> <member> <path>`, `cafe team paths [rosterDir]`, and `cafe team revoke-path <grantId>`. The `<path>` argument resolves relative to `<rosterDir>` (absolute paths are accepted only as the command's confirmation target) and must equal the member's current resolved `dir`; trust-path cannot grant an unrelated path for future use. The grant stores a random grantId, canonical roster path, member name, canonical target path, filesystem device and inode, and is mode 0600 under `CAFE_HOME`, not in the repository or replicated roster. A recreated directory at the same pathname has a different inode and requires a new grant. Symlink retargeting fails the canonical target check. A member may have multiple explicit grants; switching back to a previously approved exact path remains authorized until that grant is revoked.
- Revoking a grant first marks it durably revoked and removes the member from routing, then terminates its worker process group. A revoked member never becomes routable again if termination fails. Its canonical write scope remains reserved until the group is confirmed gone; sync/start reports revocation pending and refuses overlapping writers. `paths` lists active, revoked-pending, and stale grants by grantId so a path that disappeared or was recreated can still be revoked.

- Team start, sync, worker restore, and TUI registration revalidate the path and grant. An active worker with an external grant gets a periodic identity check; if the path disappears, resolves elsewhere, or changes device/inode, the daemon removes it from routing and stops it. Do not silently fall back to the roster root.
- Before normal reconciliation, revoke and stop any worker whose member was removed or whose write grant/access was narrowed, even if another unrelated roster entry fails validation. Then preflight every remaining member path and access rule before applying unrelated worker changes. This safety-stop exception prevents a failed preflight from leaving stale write authority running.


### Write-scope conflicts

- Compute canonical write scopes from the last successfully committed local roster plus active managed workers, not from uncommitted file edits. Every configured `write` member reserves its canonical directory whether selected, stopped, failed, or in restart backoff. A partial `team start` checks against all committed members and current supervised workers before launching anything.
- A roster TUI member has unmanaged permissions and reserves its canonical directory as a potentially write-capable scope, whether online or offline. The [TUI roster compatibility amendment](2026-11-28-tui-roster-compatibility-design.md) permits the root TUI orchestrator and separate nested TUI worktrees in the same roster. A managed read-only worker may share directories. A managed write worker may not overlap another managed write or TUI scope.
- Removed or invalidated TUI entries become unroutable immediately, but their last canonical directory remains reserved until the operator confirms the terminal was closed with `cafe team release-tui <reservationId>`. `cafe team paths --stale` lists reservation IDs and old scopes even when the roster directory no longer exists. A changed TUI directory creates a stale reservation for the old path and a normal reservation for the new path; releasing one never clears the other.
- A write-enabled member may not be launched into a directory already owned by a different live Cafe-managed write worker, including a non-team worker. All scopes use the same realpath/device/inode normalization; nested paths overlap when one is an ancestor of the other.
- Configured but unstarted or intentionally stopped roster members retain their reserved write scope to prevent a later partial start conflict. A scope is released only after a committed roster removal/read-only change or an explicit TUI release, and only after the process group is confirmed stopped.


### TUI identity

- A TUI-only roster becomes authoritative through explicit `cafe team sync` (or `team start`, which also publishes); it does not require a managed worker to exist.
- A team TUI process captures `memberLaunchHash` once when the extension loads. It covers canonical rosterRootId, team name/channel, member name, mode, effective agent/bin, canonical directory, member channels, observer, and collect. It excludes terminal-managed access and model settings, as well as live context fields such as duty aliases, description, tags, and scope. It sends the same value on reconnect and never recomputes from a changed live file. The Daemon compares it with the last locally committed member hash, not an uncommitted `.cafe` edit or client-supplied revision. A new/changed TUI can register only after `cafe team sync` commits its local roster. A reported cwd must match the committed canonical member directory as a consistency check, but remains client-reported. The actual TUI runtime/model and file permissions remain host-controlled; the hash does not claim otherwise.
- When `team sync` commits changed launch-critical fields, an already-connected TUI with a stale memberLaunchHash is immediately marked offline and its connection is removed from routing. Unrelated roster changes do not invalidate it; duty/description/tag/scope changes can update the playbook live. A team/channel/channels/observer/runtime/directory/model change requires the person to reload the terminal.
- The reported TUI cwd is a consistency check for routing and user mistakes, not a filesystem security proof: the process can self-report it, and Cafe cannot control tools in that terminal. TUI entries therefore never grant a managed worker filesystem scope or claim enforced permissions.
- A worktree copy may locate the authoritative roster through `CAFE_TEAM_DIR`, but it cannot override the effective member directory or launch hash from that roster. The client captures the hash at startup and keeps it stable for its lifetime.
- Removing or invalidating a TUI member cannot stop the terminal process. After local commit it is immediately unroutable and marked stale/offline; its old directory remains reserved until `team release-tui <reservationId>` confirms closure. A separate supervised Codex `--tui` adapter remains host-managed and must not advertise Cafe-enforced filesystem access.

### Roster reconciliation

- Add `cafe team relocate <oldRosterDir> <newRosterDir>`. The local operator credential authorizes moving the exact saved owner from the old canonical path to a new existing, valid `.cafe` root on the same Host. Refuse if the destination already has an owner. Before stopping anything, durably write a `relocating` intent with rosterRootId, old/new paths and hashes, worker process-group identities, and stale TUI scopes; restore sees this fence first and never respawns source workers. Stop all managed groups and wait for exit, mark old TUI reservations stale, and clear old-root grants. Then atomically commit the destination roster hash and ownership path, clear the relocation intent, and publish the new roster. A crash resumes the intent and finishes stopping/commit; it never rolls back to old start snapshots. If stop cannot complete, keep the relocation fence and old scopes reserved, mark affected workers offline, and refuse team start/publish until resolved. Root unavailability after local commit reports `publish pending` and retries; the operator re-approves external paths at the new root and uses stale reservation IDs to release old TUI scopes after closing terminals.
- Local roster ownership is keyed by Host plus canonical real roster path, not mutable team/channel names. On upgrade, a legacy `(host, team, channel)` owner record migrates only if its stored realpath matches; old keys become tombstones. Renaming the team/channel at the same roster path updates the same owner and retires the old Root record after successful publish. A different path cannot claim it without explicit ownership transfer.
- `team sync` reconciles existing local managed workers for the same canonical roster root. It stops removed members and restarts previously running members whose effective `agent`, `bin`, `model`, mode, canonical `dir`, access, or launch environment changed. Description/duty/channel-only changes update roster context without restart. `team sync` does not start newly added members or members that were intentionally stopped; `team start` remains the explicit start/fill-gaps command. Persist start intent per member so restore/sync can distinguish wanted, stopped, and newly added workers.
- The Daemon, not only the CLI, reads the canonical roster for sync. If the file is unreadable or structurally invalid, stop all managed workers for that roster, disconnect its TUI registrations, mark it invalid/offline, retain stale TUI/path reservation records, and do not publish. If it parses but contains identifiable invalid/removed members or revoked grants, stop those affected members before unrelated validation; leave unchanged workers alone. If another valid member fails preflight, do not apply unrelated changes.
- Safety revocations happen before unrelated validation: stop a worker whose member was removed, whose required path grant was revoked/changed, or whose access was narrowed. Persist a `revoking` record with process-group ID/start-time, canonical scope, and grant ID before signaling; wait for the entire group to exit before releasing its write-scope reservation. If termination fails, mark it unroutable, retain the scope and revoking record across daemon restart, report `revocation_pending`, and refuse overlapping writers. A stop failure prevents roster publication. If the full roster later fails preflight, unchanged workers stay as they were, while safety-revoked workers remain stopped.
- For a valid roster, preflight all paths, grants, runtime allowlists, and scope conflicts before other worker changes. Stop changed workers and wait for exit, then atomically persist the committed local roster hash, launch specs, start intent, grant revisions, and pending Root revision. If persistence fails, leave changed workers stopped and do not publish the new roster. If restarting a previously running worker fails after persistence, leave it offline with a clear error and still publish the valid desired roster; do not restore stale wider permissions. `team sync` never starts a newly added member by this path.
- Publish the roster to Root with an acknowledged `(host, rosterRootId, baseRevision, revision, contentHash)` request. Root atomically persists the new roster and any old-key tombstone before acknowledging. Equal revision/equal hash is idempotent success; equal revision/different hash, stale baseRevision, or an older revision returns `revision_conflict` with Root's current revision/hash. A lost acknowledgement retries the same request. If Root is unreachable or lacks the ack capability, local desired state remains committed/active, status reports `publish pending` (never `synced`), and retries continue after reconnect/upgrade.
- Persist the last Root-acknowledged revision/hash, every locally sent-but-unacknowledged snapshot hash, and the latest desired snapshot. On reconnect, fetch Root's current revision/hash. If it equals the last acknowledged state or a known pending snapshot, rebase the latest desired roster onto Root's current revision and send one new compare-and-swap request. If it matches none of the locally known states, report `revision_conflict` and require an operator to inspect/re-sync; never overwrite an unknown Root edit. Equal-revision/different-hash conflicts do not advance local published state. A team/channel rename at one rosterRootId tombstones the old Root key and upserts the new one in the same durable Root write.
- On daemon restore, compare persisted worker launch snapshots with the last committed local roster and current grants before respawning. Never resurrect a removed member, old directory, or old access level. If `.cafe` differs from the committed hash, keep affected workers stopped until explicit sync. Identical semantic roster sync does not restart workers.
- TUI members are never launched/restarted by Cafe; when memberLaunchHash changes, disconnect and mark the session unroutable until it reloads. Removed TUI sessions retain stale reservation IDs and require manual close plus `cafe team release-tui <reservationId>` before the old scope is freed.

## Acceptance criteria

1. A managed headless pi/omp member with omitted access or `access: read-only` has only the runtime-specific built-in read set and Cafe tools. It has no bash/edit/write, MCP, or automatic third-party extensions. A write request through an unlisted tool is impossible because the tool is absent.
2. If a Pi/OMP binary lacks the exact required flags or its executable/extension hash has no passing no-model isolation probe, team start/restore refuse before process creation; they do not display a running read-only worker.
3. Codex/Claude keep their existing sandbox and tool behavior. Valid legacy TUI `access` is ignored with migration guidance. The TUI status reflects terminal-managed permissions.
4. A relative member directory within the canonical roster root is accepted. `../`, absolute, symlink-escape, and non-canonical external paths are rejected absent an exact local grant. `trust-path` resolves the approved member target from the roster root, records realpath plus device/inode, and requires renewed approval after path retargeting or directory recreation. Switching to a separately granted exact target is allowed; revoking it is immediate.
5. A local grant permits only its exact canonical roster/member/path tuple. Revocation stops the worker before releasing its write scope and removes the member from routing even if another unrelated roster entry fails validation.
6. Two write-enabled members with identical or nested overlapping canonical directories are rejected before any selected worker changes. Stopped, failed, restart-backoff, unselected, and offline TUI members still reserve configured write scopes; managed read-only workers may share directories.
7. A TUI member whose reported cwd or startup-captured memberLaunchHash differs from the last committed roster cannot register or stay routable. Cwd is a consistency check, not sandbox proof. Unrelated roster edits do not invalidate it. Removed/changed TUI paths remain reserved until `team release-tui` confirms closure.
8. `team sync` stops removed or newly unauthorized managed workers, restarts previously running members whose effective launch config changed, and does not start newly added or intentionally stopped members. Parse/structure failure stops all managed workers for that roster; a parseable per-member error safety-stops only affected members. Stop failure keeps the scope reserved and blocks publication; restart failure leaves the valid desired roster published with that member offline. Restore never resurrects stale launch snapshots.
9. Local roster ownership and write reservations remain stable across team/channel rename at the same canonical roster root. `team sync` on another path refuses; explicit `team relocate` moves ownership on the same Host in one local transition, stops managed workers, marks TUI reservations stale, clears old-root grants, and either publishes or reports `publish pending` without restoring old workers.
10. Root publish requests are acknowledged and idempotent: equal revision/hash replays success, revision/hash conflicts do not overwrite Root state, and a lost reply retries the same request. Root acknowledges only after durable persistence.
11. Existing in-repo `.worktrees/...` team layouts continue working without grants. Legitimate external/sibling worktrees work only after an exact local grant.
12. Tests cover traversal, symlink escape, grant revocation after path deletion/recreation, scope reservations across partial starts/TUI, per-runtime read-only tool filtering, unsupported Pi/OMP flags, stale worker reconciliation and failure recovery, TUI launch-hash/cwd mismatch, Root publication retry, and persistence across daemon restart.
13. No production Root restart, external ledger edit, npm publication, or physical second-Host claim is part of local verification.
